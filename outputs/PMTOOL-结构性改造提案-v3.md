# PMTOOL 结构性改造提案 v3

> 2026-10-27 · 对 v2 的自我否定 + 一条真正需要动的路子
> 定位不变：**实施经理的个人工作平台 · 纯单机 · 零服务端**

---

## 0. 先说 v2 错在哪

v2 的 12 项里，**9 项是"在现有表上做视图"**：健康总览、每日摘要、静默时段、批量顺延、⌘K、FTS5、指标段、清单模板、骨架模板。它们不新增任何领域对象，也不减少任何一个录入动作。它们让**已经录进去的数据更好看**——而成本从来不在"看"，在"录"和"对不上"。

这不是感觉，是代码事实：

**① 同一件事，现在有 9 个入口可以打字放进去**

| 录入面 | 落表 | 服务 |
|---|---|---|
| 主工作区快速添加 | `todos` | `todo.ts` |
| 任务中心快速收集 / 周期任务 | `todos` | `todoCenter.ts` |
| 项目计划任务 | `project_tasks` | `projectTasks.ts` |
| 每周工作情况及下周任务 | `weekly_entries` | `weeklyEntries.ts` |
| 风险登记册 | `project_issues` | `projectIssues.ts` |
| 需求登记册 | `project_requirements` | `projectRequirements.ts` |
| 问题登记册 | `project_issue_log` | `projectIssueLog.ts` |
| 其他待办事项 | `project_todo_items` | `projectTodoItems.ts` |
| 今日工作内容 | `work_notes` | `workNotes.ts` |

**② 四张登记册是同构的**（`database/migrations/0016_register_tables.sql:14-70`）：都是 `project_id + 标题/内容 + 人 + 计划日 + 状态 + 进展说明 + 实际完成日`。风险、需求、问题、待办只是同一张表换了列名。

**③ 全部迁移里没有任何"承诺 / 依据 / 原话 / 交付物"字段**（`grep -rin "commitment|promise|evidence|原话|交付物" database/migrations/*.sql` → 0 命中，只有注释里的"设计依据"）。也就是说：

> 客户在周会说"服务器周五到，UAT 推迟到 11-01"这件事，系统里**没有一处能记成"客户对我的承诺 + 原话 + 到期日"**。它只能被拆成：风险登记册一条、问题登记册一条、下周一待办一条、今日工作内容一行——四份互不相干的记录，之后没有任何一处能回答"客户答应的事兑现了没有"。

**④ 后果**：任务中心的"四源聚合"（`services/todoCenter.ts:1-20`）本质上是在给 ① 打补丁——同一个待办散在 4 张表里，所以要写一层聚合把它们读回来。这是结构问题的症状，不是解法。

**结论**：v2 应该撤回。继续加视图，等于承认"录入成本"和"事实对不上"这两件事永远不解决。

## 1. 主张：从"表格录入器"改成"方法论执行器 + 交付记忆"

一句话：**现在是"人填表给系统看"，应该变成"系统记住人做的事，并替人生成交付物"。**

三层结构：

```
Playbook（你实施一个产品线的标准打法）
   └── 项目 = 一个 playbook 实例（阶段 / 交付物 / 检查项 / 验收标准 / 常见风险）
         └── 记录流：现场 15 秒记下的事实，挂到节点上
               ├── 定性 → 事项（风险/需求/问题/待办/交付物）
               └── 定性 → 承诺（我方↔客户方，谁答应什么、何时、原话）
                     └── 报告 / 验收包 / 偏离说明：由事实组装
                           └── 项目收尾：偏离与解法回写 playbook（跨项目复利）
```

四个结构动作，每一个都**要么删掉现有东西，要么新增一个以前不存在的对象**——否则不算改造。

### A. Playbook：让系统知道"一次实施该有哪些交付物"

| 项 | 内容 |
|---|---|
| 新增对象 | `playbook`（产品线/行业 → 阶段 → 交付物 → 检查项 → 验收标准 → 常见风险） |
| 项目变化 | 新建项目不再"填编号+名称再手搭 WBS"，而是**选 playbook → 生成全部阶段、任务、交付物、检查项**，再按客户情况裁剪 |
| 删除/替换 | 模板中心的「项目文件模板」并入 playbook 附件；v2 的 6 号"骨架模板"撤回（它只是 playbook 的残影）；Excel 骨架导出保留为 playbook 的一种输出格式 |
| 为什么是实质 | 今天产品对"实施"这件事**一无所知**，它只是一个空表。Playbook 让产品第一次拥有领域知识，且这份知识随项目回写而增值 |
| 验收 | 新建 WMS 项目：选 playbook 后 ≤5 分钟得到 5 阶段 + 23 任务 + 6 交付物 + 40 检查项；裁剪操作可撤销 |

### B. 记录流：把入口从"9 个"收成"1 个"

| 项 | 内容 |
|---|---|
| 新增对象 | `capture`（时间戳 + 原话 + 项目/节点可后补 + 定性结果） |
| 交互 | `⌘N` 唤起，打字/粘贴/截图，回车即存；**先记后定性**（任务 / 风险 / 承诺 / 纪要），允许"暂不归类" |
| 删除/替换 | 今日工作内容手写（改由记录 + 完成事项自动成文）；任务中心"快速收集"；登记册的空白行录入（改为从记录定性生成） |
| 为什么是实质 | 现在任何记录都要求你先判断"这属于哪个页签、哪张表、哪一列"——这一步就是实施经理不填表的原因。收件箱把判断推迟到你有空的时候 |
| 验收 | 从打开产品到记下第一条 ≤15 秒（5 次计时）；一条记录 3 次点击内可定性并挂节点；未定性记录每日提醒不超过 1 次 |

### C. 事项合一 + 承诺：把 6 张表收成 2 个对象

| 项 | 内容 |
|---|---|
| 新增对象 | `item`（type=风险/需求/问题/待办/交付物 + 状态 + 责任人 + 计划日 + 证据引用）与 `commitment`（方向：我方承诺/对方承诺；谁；什么；到期；原话；兑现状态） |
| 删除/替换 | `project_issues` / `project_requirements` / `project_issue_log` / `project_todo_items` 四表合一为 `item`；四张登记册页面变成"按 type 过滤的同一张表"；周报"下周计划"手填表退化为 items 派生视图 |
| 不改 | **Excel 导入导出格式保持原样**（客户要的四张表照旧导出，只是背后是 items 的四个视图）——这是能不能落地的关键 |
| 为什么是实质 | 现在"客户答应给环境"这种两方承诺无处安放，只能降级成一条风险或一条待办，责任方与依据全丢。承诺成为一等对象后，"验收扯皮"才有证据 |
| 验收 | 同一条事实只录 1 次（抽查 20 条落库路径）；承诺可回答"本周到期未兑现 N 条"；四张 Excel 导出与现有客户模板逐列一致（抽样 3 个项目 diff 为 0） |

### D. 事实报告 / 验收包：报告不再靠回忆写

| 项 | 内容 |
|---|---|
| 变化 | 报告 = 选范围（项目/周期）→ 按槽位组装（节点进展、承诺兑现、事项变化、交付物状态）→ 你只改措辞；验收包 = 交付物签收 + 承诺兑现 + 偏离说明的时间线导出 |
| 删除/替换 | `reportBuilder` 的"自由文本 + 完成待办拼编号列表"（`services/reportBuilder.ts`）退为兜底；周报里的手填段落改由事实生成 |
| 为什么是实质 | v2 的"指标段"只是给流水账加一行数字；这里换的是报告的信息来源——从"你记得什么"变成"系统记下了什么" |
| 验收 | 周报耗时 30–40min → ≤10min（3 周计时）；报告中每条陈述可点开看到来源记录（可追溯率 100%） |

## 2. 分阶段：先加后减，不动 9249 行也能起步

`pages/ProjectDetailPage.tsx` 已有 **9249 行**。任何一次性重构都会拖死。所以顺序是：**先旁挂新增，跑顺了再合并旧表。**

| 阶段 | 内容 | 时长（单人） | 风险 |
|---|---|---|---|
| **S1 旁挂** | 内置 1 条通用实施 playbook + 实例化生成骨架；记录流（新表 `capture`）上线；现有 8 页一行不改 | 4–6 周 | 低（纯新增，不动旧数据） |
| **S2 减法** | items 合一（四表 → 一表 + 四视图）、承诺实体；新旧双写 2 周后再切；Excel 映射保持不变 | 4–6 周 | 中高（迁移 + Excel 映射 + 报告取数） |
| **S3 产出** | 报告/验收包由事实组装；周报手填表退化为只读 | 3–4 周 | 中 |
| **S4 复利** | 项目收尾：偏离与解法回写 playbook，形成"这家客户这类问题的标准解法" | 持续 | 低 |

**如果只能投 1 个月**：只做 S1 的 playbook 部分（不含记录流）。价值仍在（新建项目从 2–3 小时降到 5 分钟、交付物不再漏），但录入面仍是 9 个——这一点必须提前认。

## 3. 怎么证明这次是"实质"（可测）

| 指标 | 现状（代码事实） | 目标 | 怎么测 |
|---|---|---|---|
| 同一事实录入次数 | 2–4 次（9 个入口 / 6 张可放同一件事的表） | 1 次 | 抽查 20 条事实的落库路径 |
| 录入面数量 | 9 | 2（记录流 + 事项） | 代码中可写入口计数 |
| 打开到记下第一条 | 要先选页面/表/列 | ≤15s | 5 次计时 |
| 新项目建架 | 2–3 小时手搭 | ≤5 分钟实例化 | 计时 |
| 周报耗时 | 30–40 分钟 | ≤10 分钟 | 3 周计时 |
| 客户承诺可检索率 | **0**（schema 无字段） | 100% | 抽查「客户答应的事」能否一条查出 |
| 交付物漏项 | 不可统计 | 检查项完成率可见 | playbook 清单完成率 |
| 报告可追溯率 | 0（纯文本） | 100% | 每条陈述能点开来源 |

## 4. 风险与"什么时候该停"

| 风险 | 判据（不满足就停，别硬做） |
|---|---|
| Playbook 做成"又一个模板中心" | 若它不能生成交付物 + 检查项 + 验收标准，只是文档模板，**立即停** |
| 记录流做成"又一个笔记" | 若一条记录不能定性、不能挂节点、不能进报告，**立即停** |
| 四表合一迁移失控 | 先双写 2 周 + 迁移前快照；Excel 导出 diff ≠ 0 就回滚 |
| 范围膨胀 | 一旦出现"多人/权限/审批/客户登录"，直接判死（这是 C1/C2，不是偏好） |
| 精力不足 | 单人 3 个月是底线。若排期 <1 个月，只做 playbook，不做记录流与合并 |

**仍然不做**：AI（另文，本轮不做）、团队协作、CRM/回款、工单/SLA。
